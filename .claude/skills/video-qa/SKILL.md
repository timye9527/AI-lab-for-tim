# 视频总质检员

底线：**成片里不能有普通人一听一看就能发现的错，也不能再犯错误档案里犯过的错。**
做法：**先定、再配、后渲。** 每一关过了才进下一关；越往后改越贵（渲染一次几分钟到一个半小时）。

同目录文件：
- `错误档案.md`：7 个项目踩过的坑和防线。**开工先读「零、每次必查」**，做到哪关再看对应的节。
- `选型速查.md`：声音、画面、配乐选哪条路，各模型的毛病和要手动处理的地方。
- `docs/VIDEO-GUIDE.md`（仓库根）：给主理人看的新手指南：流程、下单模板、什么费 token / 流量 / 时间 / GPU。

项目自己有质检（例如内容工厂分支的 `video-qc`、存储视频的 `pronounce.py`）时两个都用：项目的管细节，这个技能管流程和跨项目的坑。

## 开工前（不超过 2 分钟）

1. 读 `错误档案.md` 的「零」。
2. 找能复用的东西：这个仓库各分支已经有 7 条管线（分支表在错误档案开头）。同类视频优先在已有管线上改，不从零写。
3. 填需求卡（下面），**缺的项一条消息问齐**，不要边做边问。

## 关卡

| 关 | 做什么 | 过关条件 | 主理人要拍板吗 |
|---|---|---|---|
| G0 需求卡 | 填下面的卡 | 卡上每项都有答案 | **要**（一次问齐） |
| G1 稿件 | 写稿、核事实；跑 `npm run video:lint -- <稿件>` | ✗ 为 0；⚠ 逐条处理完（改写或确认无误）；估算时长符合目标 | 过稿时一起看 |
| G2 读音 | 管线生成逐句拼音的读音表；坑词、人名、行业词进覆盖表；新英文缩写验证读法 | 「待确认 / 重点审」为 0；把送进模型的文本跑 `video:lint -- <文本> --tts`，✗ 为 0 | 有争议的读音才问 |
| G3 声音样片 | 合成 30～60 秒样片：**选全片最难的一段**（数字、英文、人名、多音字最多），配 1～2 张关键帧 | 主理人确认音色、语速、情绪、画风 | **要**。确认后把参数写进项目 README 的「定稿参数」，后面不再改 |
| G4 全量配音 | 逐句合成 + 回听（语音识别逐音节比对），不对就重读，8 次不过就改写 | 回听全过；自己听前 30 秒和每章开头；读音表复看一遍 | 不用 |
| G5 关键帧 | 不渲染视频，只出静帧拼图（一张 3×3） | 没有孤字、越界、压字幕、折行；首帧能当封面；画面文字不写具体时长 | 不用（大改版式才问） |
| G6 渲染 | 后台跑；有预览档就先出低清预览 | 渲染成功 | 不用 |
| G7 成片体检 | `npm run video:final -- <成片> --platform <平台> --srt <字幕> --sheet <拼图>`；管线有成片回听就再跑一遍 | ✗ 为 0；△ 逐条确认；拼图看过 | 不用 |
| G8 交付 | 按汇报模板交付；发布包（标题、封面、简介、章节、AI 生成标识、免责声明） | 汇报写清楚查了什么、没查到什么 | **要**（最终确认） |

**只在 G0、G3、G8 打扰主理人。** 其他关卡自己过，过不了就修，修不了再问。

### G0 需求卡

```
平台和画幅：抖音 / 视频号 / 小红书（9:16）、B 站 / YouTube（16:9）、Shorts
目标时长：
声音：真人录音 / 本人声音克隆 / AI 男声 / AI 女声；风格参考（例：沉稳解说、温暖讲故事）
画面路线：程序化动画 / 数据图表 / 录屏图解 / AI 视频生成（要花钱、要主理人账号）
素材：原稿、出处、照片（用途）、logo；哪些不能出现
配乐：要不要、什么情绪（只用原创或有授权的）
截止时间和预算（默认 0 元、只用本机）
发布要求：AI 生成标识、免责声明、封面文案方向
```

## 改了东西从哪一关重跑

| 改了什么 | 从哪重跑 | 不要做的 |
|---|---|---|
| 一两句台词 | G1 只 lint 这几句 → 只重配这几句 → 读音表看这几句 → 只重渲时间轴变了的段落 → G7 | 不要整片重配、整片重渲 |
| 读音（多音字） | 覆盖表加词 → 只重配这句 → G7 | 不要只改指令不听结果 |
| 换声音 | 回 G3 出样片确认 → 全量重配 → 时间轴变了就 G5 | 不要不出样片直接全片 |
| 画面版式 | G5 拼图确认 → 只重渲受影响的段 | 不要改一次渲一次全片 |
| 配乐 | 单独导出配乐听 10 秒 → 重混 → G7 | 不要只听混音后的成品 |
| 字幕文字（口播不变） | 改字幕文件；烧进画面的只重渲字幕层或受影响的段 | — |

## 发现新错误时（包括主理人反馈）

1. **先查成品证据**：去听、去看那一处，确认现象，再回应。不要先拿词典、规则解释。
2. 修掉。
3. **让检查能抓到它**：读音类加进 `scripts/video-lint.mjs` 的 `TRAPS`（坑词）或 `RULES`（模式）；成片类加进 `scripts/video-final.mjs`；项目质检有漏网就改项目质检。确认它能报出来。
4. 在 `错误档案.md` 对应的节加一行（现象、例子、根因、防线）；通用的、代价大的也写进「零」。
5. 主理人表达的偏好写进错误档案「十、主理人偏好」。

## 交付汇报模板

```
成片：<路径或链接>（时长、画幅、大小）
过了哪些关：稿件预检 ✗0 ⚠N（怎么处理的）；读音表审 N 处；回听 N 句通过，其中 N 句重读，改写了哪几句、为什么；成片体检结果
没查到的：回听听不出声调和多音字（靠读音表和人耳，我听了哪些段落）；事实以出处为准，待核实的 N 条
需要你做的：（只列真正要主理人动手的）
用时和花费：渲染 N 分钟；有没有用付费服务
```

## 省 token、省时间（给自己的规矩）

- **最大的浪费是返工**：G0 问齐、G3 先出样片，比任何技巧都省。
- 读大文件先 `grep` 定位，再 `sed -n` 看几十行；不要整读 800 行的画面文件。
- 看画面用一张 3×3 拼图（`video:final --sheet` 或管线的 stills），不要一张张看全尺寸截图；只在 G3、G5、G7 看图。
- 渲染、合成、下载这类长任务放后台跑，完成会通知，不要反复轮询；ffmpeg 加 `-loglevel error`，只看结尾几行。
- 报告只打印不通过的项（`video:lint` 默认每条只列 6 处）。
- 改稿时给主理人看改动的句子，不要每次贴全文。
- 逐句缓存、只重配改过的句子；只重渲受影响的段。
- 4 核机器上不要并行开多个 Chromium 渲染，反而更慢。
- 模型、字体、数据下载一次放进忽略目录（`out/`、`.cache/`）；成片、模型、`__pycache__` 不提交。
